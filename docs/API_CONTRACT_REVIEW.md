# Antigravity API contract review · 2026-11-23

Reviewed the complete Antigravity handoff at `7ca0d22` against Fastify, its OpenAPI file, the published-reader SQL views, the five private staging receipts and the task dependencies. The 13 browser resources below are the integration contract. They specify 15 method/path combinations. Only `GET /health` currently has a Fastify handler. The resource names are accepted. The corrections below apply before implementation. [Antigravity handoff](UI_TO_CODEX_API_CONTRACTS.md) · [Feature checklist](ANTIGRAVITY_CHECKLIST.md) · [Architecture](BIBLE_DATA_ARCHITECTURE.md)

## Rules shared by the resources

- A successful response carrying Scripture, book metadata, a Bible citation or an edition-specific study result carries the immutable edition ID and archive version, the action the server authorized and its verified status, attribution, terms, conditions and evidence URLs. Bind each citation or mixed-edition result to the appropriate context. A catalogue carries this information on each item. Empty catalogues are valid. A denial or outage returns an error without Bible text. A commercial-use grant describes a permission. D-001 remains undecided.
- Use published source versions and server-selected grants for the operation. Public reader views enforce host and display, evidence, attribution and model-compatible commercial rights. Check cache, index, retrieval, offline, external AI, embeddings, speech and recordings separately at their actual use sites. A display grant never implies permission for any of these. KJV has no worldwide publication authorization. Both IRVs retain external AI, embedding and synthesized-speech holds. Preserve CC BY-SA attribution and notices.
- A source address is `editionId + version + bookId + chapterLabel + verseLabel`. A row ordinal controls pagination. A standard verse key is supplied only through a verified mapping. Comparative eligibility belongs to the pair of versions and the covered range. Return the mapping revision and explicit splits, merges, bridges, omitted/unmapped rows and alternate numbering. With no verified mapping, disable aligned mode. Independent side-by-side reading can keep independent positions.
- Only reviewed, published source rows may supply Scripture. Keep introductions, headings, notes and commentary separately typed. The API never substitutes another translation, fabricated wording or examples on a denial, an empty result or an outage. Frontend fixtures require an explicit demo mode with persistent labelling. In live mode, show unavailable/error states. An edition change clears incompatible cached content.
- Each user endpoint requires authenticated identity from the server and per-user authorization. Client-side focus effects remain ephemeral. Saved annotations and persistent reading preferences have separate storage and consent. Search queries, user notes and reading history require privacy-aware logging.

## Integration decisions and acceptance checks

### Disposition of Antigravity's follow-up at `51f2913`

Antigravity committed its response while verification was running. Codex accepts its version-bound cursor, literal labels and unavailable-state conventions. Several proposed shortcuts would conflict with the owner's rights and alignment requirements. The following decisions apply to the handoff. [Frontend acknowledgement](ANTIGRAVITY_CONTRACT_ACKNOWLEDGEMENT.md)

| Acknowledgement item | Integration decision |
| --- | --- |
| 1 · Source labels and deep links | Use the literal source label in a deep link scoped by edition, version, book and chapter. A concatenated printed reference has meaning within that edition only. Reserve standard keys for OC-05 verified mappings. |
| 2 · Cursor | Accept the version-bound cursor, null at exhaustion and 409 recovery. Discard stale rows together with the cursor when reloading. |
| 3 · Position | Accept optional scroll fraction on initial write, default zero, and a server timestamp on response. Accept legacy keys in the frontend adapter only when their edition/version and source address can be resolved unambiguously. A client timestamp cannot establish server revision. Anonymous progress remains local. |
| 4 · Switching editions | Restore the target edition's own previously saved versioned position when available. For cross-edition transfer use a verified mapping; otherwise offer independent navigation to an available book/chapter. An approximate visual scroll may be indicated as such and must not become an equivalent verse or overwrite a saved position. Missing books prompt an explicit selection from the authorized catalogue. |
| 5 · Telugu/English comparison | Linked rows, spacers, passage transfer and synchronized scrolling require server-provided reviewed mappings for both versions and the requested range. Matching by label, ordinal or bridge prefix is excluded. Both pilots have 36 markers in John 3, but their NT totals are WEB 7,958 and Telugu IRV 7,875. Telugu MAT 1 has one `22-23` row. Preserve the literal row. |
| 6 · Picker and offline catalogue | Accept canon-aware section metadata once reviewed. Deuterocanonical OT material can carry a separate picker section, and appendix membership is explicit. A cached catalogue must match the edition/version and the required grants. A static 66-book list cannot represent an unavailable Catholic or Orthodox edition. |
| 7 · Errors | Accept 400/401/404/409 and an empty successful catalogue. Offer recovery links only for currently available editions/passages. Keep live service errors distinct from demo data. |

The architecture's service paths may be mapped behind these browser resources. The service schema and browser schema have different field names. Contract tests should cover the actual browser adapter before connecting the UI. Additional checklist ideas such as streamed assistant responses, geography tiles and a focus-profile sync are outside the 13-resource handoff and have no live contract. [Reader mapping and examples](../packages/contracts/reader-proposal.md)

Antigravity's reader currently calls local fixtures for both editions and slices chapter arrays independently. Its API client only fetches health and can return a mock success after failure. Before live integration, the UI must distinguish an unavailable API from healthy state, remove the live fixture fallback, consume the edition context and original labels, and enable linked scrolling only for verified mapped rows. A 404, 403, offline error or empty catalogue must never display demo Scripture as an actual translation. Codex owns the API and versioned contract. Antigravity owns these frontend changes.

Review examples include a DRA-only book, a metadata-only Orthodox profile, a Telugu bridge, a BSB gap, a WEB note-only marker, a withdrawn publication, two editions with equal printed numbers and no mapping, and a held KJV request. Live Fastify routes await approval of the corrected payloads and their individual dependencies.
